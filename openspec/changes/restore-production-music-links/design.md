## Context

生产入口为 `https://site.shizuki.online`，解析到个人站服务器 `111.228.35.186`。外部请求经网关进入前端 Nginx，再转发到 monolith backend；播放解析可能继续访问 Meting sidecar、网易云账号 sidecar、Redis/数据库缓存和音乐平台上游。当前现场信号是健康接口与曲目元数据正常，但默认曲目的 `audio`、`lyric` 为空，因此必须把“服务存活”与“曲目可播放”分开验证。

服务器配置可能含账号 Cookie、API Token、数据库密码和短时音频地址。诊断记录、文档、脚本输出及 Git 提交均不得包含这些值。仓库已有未归档音乐功能变更，本次工作只处理生产可靠性与运维知识，不重做播放器功能。

## Goals / Non-Goals

**Goals:**

- 用一个秒级、无人值守、可重复的检查命令复现“曲目存在但播放链接不可用”。
- 给后续 Agent 留下覆盖外部入口、容器网络、后端解析、缓存、账号源和上游限制的操作手册。
- 通过服务器上的只读探针和单变量实验定位根因，再实施最小、可回滚修复。
- 用修复前后完全相同的检查标准验收，并记录脱敏事故结论。

**Non-Goals:**

- 不访问或部署到 `111.228.52.91`。
- 不绕过音乐平台版权、地区、登录或会员限制，不导出用户 Cookie。
- 不顺带升级整个技术栈、重写播放器或清理无关容器。
- 不把一次临时上游成功当作永久可靠性保证。

## Decisions

1. **以真实播放解析作为反馈信号。** 检查先读取公开默认歌单取得代表曲目，再调用产品实际使用的解析入口并验证非空媒体地址及资源响应。相比只查 `/actuator/health` 或 Meting `/health`，该信号覆盖用户遇到的真实失败路径。

2. **文档按链路分层，而不是按文件罗列。** 手册使用“浏览器 → 网关 → backend → 缓存/数据库 → sidecar → 上游”的顺序，并为每层记录症状、命令、判据和安全修复。这样能在实现文件变化后仍保持可用。

3. **服务器检查先只读、后单变量。** 先采集 Compose 状态、健康、脱敏配置存在性、目标日志和容器内请求；只有某个可证伪假设被验证后才修改一个配置或重启一个相关服务。相比直接全量重建，能缩小影响和保留因果证据。

4. **运行时热修复必须回写仓库。** 若根因位于服务器 `.env.server` 或容器运行状态，先恢复服务，再把非敏感默认值、说明或检查脚本同步到仓库，避免下次部署重新引入问题。秘密仍只保留在服务器环境文件或既有私有配置中。

5. **输出按字段脱敏。** 检查只输出 HTTP 状态、阶段、provider、track id 和域名等诊断信息；Cookie、Token、查询串和完整音频 URL 不输出。需要比较配置时仅报告键是否存在、是否为空或值哈希，不报告原值。

## Risks / Trade-offs

- [Risk] 音频链接通常短时有效，HEAD 请求也可能被上游拒绝 → 使用受限字节范围 GET 作为媒体探针，并允许脚本区分“解析失败”和“资源探测策略不兼容”。
- [Risk] 默认歌单中的单曲可能因版权变化不可播 → 手册要求至少比较一个已知代表曲目与搜索结果，只有链路性失败才修改服务。
- [Risk] 重启 backend 或 sidecar 会造成短暂中断 → 只重启被确认有问题的服务，变更前记录容器状态与回滚值，变更后立即执行冒烟检查。
- [Risk] 日志可能含上游 URL 或授权信息 → 只使用窄时间窗和字段级过滤，任何持久事故记录必须脱敏。
- [Risk] 服务器运行配置与仓库示例漂移 → 在文档中加入部署前配置核对项，并让冒烟脚本成为每次发布后的必跑检查。

## Migration Plan

1. 在仓库新增运维手册和只读冒烟检查，先在当前故障状态运行并保存脱敏失败阶段。
2. 通过 SSH 在 `111.228.35.186:/opt/shizuki-site` 执行只读容器、日志、配置存在性和容器内上游探针。
3. 对已确认根因保存脱敏前值或备份，然后只修改相关配置/服务并记录回滚命令。
4. 重跑同一冒烟检查、相关自动化测试和构建；确认真实媒体请求成功且无凭据泄露。
5. 如果修复失败，恢复保存的配置并重建或重启原服务；如果属于上游限制，回滚实验性变更并记录限制而不是扩大改动。
