## Context

项目的硬性协作规则位于根目录 `AGENTS.md`，业务设计、代码规范和部署说明分散在 `resouces/md/`、`deploy/`、各模块源码及脚本中。当前仓库是 Java 17 的 Maven 单体模块化后端加 Vite 前端，默认开发环境依赖 `D:\environment`，运行时中间件默认位于个人网站服务器 `111.228.35.186`。

本变更只增加面向智能体的 Markdown 导航层，不改变已有规则的优先级，也不把私有配置内容复制到新文档中。

## Goals / Non-Goals

**Goals:**

- 让新智能体从 `.agent/README.md` 开始，在几分钟内找到项目边界、模块职责、启动命令、测试入口和交付流程。
- 把经常需要判断的事实整理为短文档，并链接到已有的详细设计与规范来源。
- 显式标出远端服务器归属、私有配置位置、不可执行的危险操作和验证要求。
- 让文档结构易于通过 `rg`、文件名和相对链接检索。

**Non-Goals:**

- 不替代根目录 `AGENTS.md`，不复制其全部协作协议。
- 不重新设计 Maven 模块、前端架构、API 或数据库。
- 不记录任何密码、Token、私钥、真实账号或私有配置值。
- 不把一次性业务方案或全部历史文档搬进 `.agent/`。

## Decisions

### 1. 采用单一入口加主题文档

`.agent/README.md` 负责阅读顺序和快速决策；主题文档按项目地图、架构、开发运行、配置边界、测试交付和参考资料拆分。选择拆分而不是单个超长文件，是为了让智能体能按任务只读取相关上下文，并减少上下文噪音。

### 2. 保持“硬约束”和“知识导航”分层

根 `AGENTS.md` 仍是协作、服务器归属、提交和推送权限的最高优先级来源；`.agent/` 只提供解释、索引和操作入口。若两者冲突，以 `AGENTS.md`、实际脚本和当前源码为准，并在维护文档时修正索引。

### 3. 以仓库相对路径为主，外部路径显式标记

仓库内文件使用 Markdown 相对链接，便于分支和克隆迁移；`D:\environment`、本机启动脚本和远端主机等外部事实单独标注为环境依赖，不伪装成仓库文件。这样既能保留真实开发入口，也能避免智能体误以为这些资源可以提交到仓库。

### 4. 文档只保存可执行事实和来源

命令、端口、模块职责和验证步骤写入 `.agent/`；详细的设计决策、API 清单、SQL 迁移和专题方案继续引用 `resouces/md/`、`resouces/postman/`、模块源码和 `deploy/`。对于可能变化的内容注明“以脚本/配置/源码为准”，避免把文档当成第二套配置系统。

### 5. 用维护规则控制过期风险

入口文档增加文档更新触发条件：模块、启动脚本、部署目标、配置路径、测试命令或服务器边界变化时同步更新 `.agent/`。每次修改后至少执行路径存在性检查、Markdown 链接检查和 `git diff --check`；涉及代码变更时仍遵守项目原有测试门禁。

## Risks / Trade-offs

- [文档随代码变化而过期] → 入口明确源码/脚本优先，并在维护文件中列出需要同步的触发条件。
- [导航文档与详细文档重复或冲突] → `.agent/` 只保留摘要和链接，复杂规则指向已有权威来源。
- [配置示例被误当成真实凭据] → 不复制 `common-config.yaml`、`.env.server` 等私有值，只记录路径、键名类别和安全边界。
- [Windows 路径降低跨环境可读性] → 仓库内链接使用相对路径；本机依赖路径明确标注“仅当前开发机”。

## Migration Plan

1. 创建 `.agent/` 主题文档，并从入口链接根 `AGENTS.md` 和现有权威资料。
2. 用当前仓库目录、脚本和配置文件验证文档中的路径与命令。
3. 运行 OpenSpec 校验、Markdown/路径检查和可行的项目质量命令。
4. 若未来文档不再需要，可删除 `.agent/` 及本次 OpenSpec 变更；不涉及运行时回滚。
